# vetastart
VetaStart — Instagram Automation Platform

## Текущее подключение Meta: Unified login

В кабинете выбранного приложения Meta старый Instagram Login недоступен для
новых приложений. Для него нужна адаптация к Unified login. Из предоставленной
Meta ссылки подтверждены следующие несекретные значения:

```text
INSTAGRAM_LOGIN_MODE=unified
META_APP_ID=1810672910147174
META_GRAPH_API_VERSION=v27.0
INSTAGRAM_CONFIG_ID=1674463687685006
INSTAGRAM_REDIRECT_URI=https://vetastart-app-2026.onrender.com/auth/instagram/callback
```

Эти значения указаны как образец, в настройки среды и Render они не записывались.
Генератор поддерживает официальный адрес `https://www.facebook.com/dialog/oauth`
и передаёт config_id и одноразовый state, связанный с браузером. Не используйте
шаблонную ссылку Meta с буквальным `<STATE>` для входа.

Unified callback теперь обменивает код на `graph.facebook.com/{version}/oauth/access_token`
с `META_APP_ID` и `META_APP_SECRET`, получает Instagram ID через
`/me/assigned_instagram_accounts` и сохраняет зашифрованный SUAT вместе с
business ID и config ID. Отправитель Unified использует `graph.facebook.com`.
Для бизнес-ID пока нужен `META_CLIENT_BUSINESS_ID`, полученный из Meta;
автоматическое определение бизнес-ID для разных клиентов ещё не реализовано.
Если срок есть в `expires_in`, сохраняется он. Отсутствие срока разрешено только
при явном `META_SUAT_NON_EXPIRING=true`, подтверждённом настройкой конфигурации.
Иначе вход завершается ошибкой. Unified токены никогда не обновляются через
старый `ig_refresh_token`. SUAT Management API пока не реализован: истёкший
токен требует повторного входа. Схемы продления ниже относятся к старому Login.
Публикация и реальная проверка на Render не выполнялись.

## Локальный запуск

Нужен Node.js 24 или новее (используется встроенный `node:sqlite`).

```sh
npm ci
npm start
npm test
```

Сервер слушает `PORT` (по умолчанию 10000). Страница доступна без секретов.
Webhook: `GET /webhooks/instagram` для проверки Meta и `POST /webhooks/instagram`
для событий с подписью `X-Hub-Signature-256`.
Задайте `INSTAGRAM_VERIFY_TOKEN` и `META_APP_SECRET` через защищённые переменные
окружения. Не добавляйте секреты в Git.

## События и сценарии

Подписанное событие сохраняется в выбранной базе **до** ответа `EVENT_RECEIVED`.
При ошибке диска сервер отвечает 503, чтобы Meta могла повторить доставку.
Повторная доставка одного тела и одинаковые ID сообщений/комментариев внутри
одного аккаунта не создают повторные события. Echo-сообщения и собственные
комментарии пропускаются. Неподдерживаемые события сохраняются в доставках,
но не запускают сценарий.

`VETASTART_DB_PATH` задаёт путь к базе (по умолчанию `data/automation.sqlite`).
Для размещения приложения нужен постоянный диск, резервные копии и политика
удаления данных: база содержит тексты сообщений и идентификаторы пользователей.
Файл создаётся с правами 0600. База и `.env` исключены из Git и не выдаются HTTP-сервером.

Скопируйте `scenarios.example.json` в локальный `data/scenarios.json`, замените
`accountId` на ID своего Instagram, задайте ответ и включите правило.
`trigger` поддерживает `message` и `comment`. Первое подходящее включённое правило
выбирается по аккаунту, типу события и кодовому слову без учёта регистра,
по границам слов. Например, «ГАЙД!» подходит, «гайдлайн» — нет.

```sh
VETASTART_SCENARIOS_FILE=data/scenarios.json npm run worker
```

Worker обрабатывает очередь до опустошения и завершает работу. Запускайте его
повторно после новых событий или через планировщик. При отсутствии файла
сценариев worker завершится с ошибкой, не помечая события обработанными.
Ответы сохраняются в таблицу `drafts`; worker сам **не отправляет их в Instagram**.
Повторный запуск worker не создаёт второй черновик. События без подходящего
правила получают статус `unmatched`; изменение правил не переигрывает их автоматически.

## Отправка Direct через Meta

`npm run send` выполняет один проход (до 100 черновиков) и завершает работу.
По умолчанию отправка выключена. Для подключения через **Instagram Login**
задайте в защищённых переменных окружения:

- `INSTAGRAM_ACCOUNT_ID`: ID профессионального Instagram-аккаунта;
- `INSTAGRAM_ACCESS_TOKEN`: токен этого аккаунта с разрешением на сообщения
  (можно не задавать после успешного OAuth-подключения: sender прочитает зашифрованный токен из базы);
- `META_GRAPH_API_VERSION`: поддерживаемая вашим приложением версия вида `vNN.0`;
- `VETASTART_SEND_ENABLED=true`: явное включение реальной отправки.

Версию API нужно выбрать по текущим настройкам и документации приложения Meta.
Токен не помещается в URL или логи, в базе хранится только шифротекст. Отправитель использует HTTPS
`graph.instagram.com/{version}/{accountId}/messages`, Bearer-заголовок и JSON
с `recipient.id` и `message.text`. Токены от интеграции Facebook Login не следует
смешивать с этим транспортом. Для OAuth-подключения через интерфейс
необходимы настройка приложения Meta, авторизация аккаунта, нужные разрешения и
подписка webhook. Доступ для сторонних аккаунтов может потребовать проверки Meta.

Поддержана отправка ответа на входящее **Direct-сообщение** в пределах 24 часов
от его timestamp. Отправитель обрабатывает только настроенный аккаунт.
Комментарии, старые события, события без timestamp и с временем из будущего
получают `blocked`. Старые базы мигрируют без удаления данных; старые события
без timestamp не получают разрешение на отправку автоматически.

Статусы черновиков:

| Статус | Значение |
| --- | --- |
| `draft` | Ожидает отправителя |
| `sending` | Попытка начата; после аварии процесса требует сверки |
| `sent` | Meta вернула `message_id` |
| `failed` | Meta отклонила запрос HTTP 4xx; нужен разбор причины |
| `unknown` | Доставка не подтверждена: тайм-аут, разрыв связи, HTTP 5xx или некорректный ответ |
| `blocked` | Этот источник нельзя отправить данным транспортом |

Параллельные запуски атомарно резервируют черновик перед сетевым запросом.
Автоматических повторов нет, включая HTTP 429: при неопределённом результате
повтор может отправить дубликат. Сверьте `sending`/`unknown` с перепиской Meta
перед ручным решением о повторе; просто перезапускать такие записи нельзя.
После 4xx сначала исправьте доступ/настройку. Для регулярной работы планировщик
должен последовательно запускать `npm run worker` и `npm run send`.

Полная цепочка протестирована с локальной подменой API, без отправки реальным
пользователям. Реальная совместимость с вашим приложением Meta ещё не проверена:
в среде отсутствуют учётные данные. Отправка private reply на комментарий,
ИИ-ответы через OpenAI API, цепочки сообщений и интерфейс управления пока не реализованы.

## Подключение Instagram через браузер

Кнопка на главной открывает `/connect/instagram`. Для работы входа задайте:

- `INSTAGRAM_CLIENT_ID` и `INSTAGRAM_CLIENT_SECRET`: данные Instagram-приложения Meta;
- `INSTAGRAM_REDIRECT_URI`: публичный HTTPS-адрес с путём `/auth/instagram/callback`,
  точно совпадающий с разрешённым Redirect URI в Meta;
- `VETASTART_ADMIN_TOKEN`: отдельный случайный ключ доступа к подключению, минимум 32 символа;
- `VETASTART_TOKEN_KEY`: постоянный ключ AES-256-GCM — 32 случайных байта в Base64;
- `META_GRAPH_API_VERSION`: используемая приложением версия API.

Сохраните ключи в защищённых настройках окружения, не в чате и не в Git.
Ключ шифрования нужен также процессу sender и для восстановления резервной копии.
Потеря/смена ключа без перешифрования требует повторного входа в Instagram.
Никогда не используйте пароль Instagram в поле ключа администратора VetaStart.
Вводимый в браузере ключ администратора не сохраняется в localStorage или cookie.

Настройте в Meta webhook `/webhooks/instagram` с verify-токеном,
профессиональный аккаунт и разрешения `instagram_business_basic` и
`instagram_business_manage_messages`. После входа сервер обменивает короткий
токен на долгоживущий и запрашивает профиль,
подписывает аккаунт на `messages` и сохраняет токен, зашифрованный AES-256-GCM.
Если задан `INSTAGRAM_ACCOUNT_ID`, подключение другого аккаунта отклоняется.
Этот ID обязателен для sender и должен совпадать с `accountId` в сценариях.

OAuth-state одноразовый, связан с HttpOnly/Secure/SameSite=Lax cookie браузера,
истекает через 10 минут и сохраняется в SQLite в виде хеша. Callback убирает
код из URL перенаправлением; страницы подключения запрещают кеширование.
На HTTPS-прокси отключите логирование параметров callback и заголовков Authorization:
в callback URL временно находится одноразовый код. Используйте приложение через HTTPS.

После входа сохраняется долгоживущий токен со сроком из ответа Meta (не более
60 дней). Если обмен не завершён или срок некорректен, подключение не сохраняется.
Прежние короткоживущие подключения не продлеваются: выполните новый вход.

Перед каждой отправкой sender проверяет OAuth-подключение и при необходимости
продлевает токен. Дополнительно запускайте ежедневно `npm run refresh-tokens`
через планировщик, даже если отправка выключена или нет сообщений.
Планировщик в этой среде не установлен. Команда выводит только счётчики результатов
и возвращает ненулевой код при сбое продления или необходимости нового входа.

Продление начинается за 7 дней до истечения, если с выдачи/предыдущего обновления
прошло минимум 24 часа. Параллельное обновление блокируется на 60 секунд;
временная ошибка откладывает следующую попытку на час, сохраняя ещё действующий
токен. Обновление не перезапишет новое подключение, созданное во время запроса.
Истёкший токен или ответ Meta с кодом 190/HTTP 401 помечается как
`reauthorization_required`: отправка остановится, нужен повторный вход.
Здесь отзыв обнаруживается при запросе к Meta, а не отдельным webhook отзыва.

Meta требует query-параметры с секретом и токеном на `/access_token` и
`/refresh_access_token`. Не включайте логирование полных URL исходящих запросов
в прокси/APM. Код не выводит URL, тела ответов или исходные исключения этих запросов;
в базе сохраняются зашифрованный токен и обезличенный статус ошибки.

При наличии `INSTAGRAM_ACCESS_TOKEN` в окружении он имеет приоритет над
сохранённым OAuth-токеном и не продлевается этим механизмом. Сам OAuth-вход
не включает отправку. Реальную работу обмена и продления с вашим приложением Meta
ещё нужно подтвердить после настройки доступа.

Локально вход проверен подменой ответов Meta; настоящая авторизация не выполнялась.
В текущей среде перечисленные настройки отсутствуют. Никакие настройки среды
или опубликованной версии при разработке не изменялись.

## Кабинеты клиентов: тестовая основа подписного сервиса

`/app` — регистрация/вход, подключение Instagram, создание и удаление сценариев.
API `/api/customer/*` использует серверные сессии; cookie HttpOnly/SameSite=Lax,
Secure на HTTPS. Пароли хешируются scrypt с индивидуальной солью, в базе
хранится только SHA-256 сессионного токена. Срок сессии — 7 дней. Запись защищена
проверкой Origin, число попыток входа ограничено 20 за 15 минут по IP.

Задайте `VETASTART_PUBLIC_ORIGIN` равным публичному origin сайта (HTTPS, без пути
и завершающего слеша). Для локальной проверки разрешён HTTP только на localhost
и 127.0.0.1. Регистрация по умолчанию выключена; включайте
`VETASTART_SIGNUP_ENABLED=true` только в контролируемом тестировании.
Подтверждение email и восстановление пароля реализованы; требуется настроить SMTP (см. раздел ниже). При размещении за
прокси лимитер намеренно не доверяет произвольному X-Forwarded-For: настройку
доверенных прокси следует добавить перед публичным запуском, иначе пользователи
за одним прокси могут разделять лимит.

Сценарии доступны только владельцу кабинета. Привязку аккаунта нельзя задать
произвольным запросом: она создаётся при успешном Unified OAuth, привязанном к
сессии клиента. Аккаунт другого владельца переназначить нельзя. Старые
подключения администратора автоматически клиентам не раздаются. Токены не
выдаются через API кабинета. `worker` читает сценарии клиентов из SQLite;
сценарии из административного JSON не применяются к принадлежащим клиентам
аккаунтам. При полном отсутствии правил очередь не помечается обработанной.
Команда `send` запускается для выбранного INSTAGRAM_ACCOUNT_ID. Общий обработчик
в режиме automation выбирает каждый клиентский аккаунт и его токен отдельно.

Это ещё не готовый коммерческий SaaS. Не проверены реальные платежи, не подключены рекуррентные
списания, реальная доставка почты,
отдельная настройка бизнеса каждого клиента и продление SUAT. Нужны проверка
Meta для сторонних аккаунтов, постоянный диск, резервные копии, мониторинг и
реальный сквозной тест в Instagram. Изоляция кабинетов проверена локальными
тестами, но не заменяет проверку безопасности перед коммерческим запуском.

## Регулярная обработка нескольких клиентов

Для запуска вместе с веб-сервисом (`npm start`) установите:

```text
VETASTART_AUTOMATION_ENABLED=true
VETASTART_AUTOMATION_INTERVAL_MS=10000
```

По умолчанию оба режима — фоновая обработка и реальная отправка — выключены.
Без `VETASTART_SEND_ENABLED=true` обработчик только создаёт черновики. Для отправки
нужны зашифрованные подключения клиентов, VETASTART_TOKEN_KEY и версия API.
В отличие от одноаккаунтной команды send, общий обработчик не использует
глобальный INSTAGRAM_ACCESS_TOKEN: для каждого клиента берётся его токен из базы.

Каждый цикл создаёт до 1000 черновиков и обрабатывает до 25 аккаунтов, до 20
отправок каждому. Аккаунты чередуются по времени последнего прохода. Ошибка
одного подключения не останавливает остальные. Повторный цикл внутри процесса
не начнётся, пока не завершён предыдущий. При SIGTERM/SIGINT текущий цикл
завершается перед закрытием базы. После перезапуска процесс читает очередь из
SQLite; записи sending/unknown не пересылаются автоматически.

В кабинете клиента отображаются последние 50 статусов его ответов. Тексты
сообщений, токены и чужие аккаунты через этот список не выдаются. Удаление
сценария блокирует ещё не отправленные ответы; уже начавшийся сетевой запрос
отозвать нельзя.

Альтернатива для отдельного процесса на той же машине и с тем же диском —
`npm run automation`. Не запускайте его одновременно со встроенным обработчиком
без необходимости. На Render отдельные сервисы не должны рассчитывать на общий
локальный SQLite-файл: для текущей версии используйте один веб-сервис с фоновым
циклом в нём и постоянным диском. Например, VETASTART_DB_PATH должен указывать
в каталог смонтированного диска. Свойства и доступность диска в выбранном тарифе
Render нужно проверить перед размещением. Публикация здесь не выполнялась.

Обработчик не принимает оплату. Срок доступа и лимиты проверяются модулем subscriptions. Фактическая
доставка через Meta, доступ для сторонних аккаунтов и SUAT Management API требуют
отдельной проверки; локальные тесты используют подмену внешнего API.

## Срок доступа и пилотные тарифы

После подтверждения email новому клиенту один раз выдаётся пробный период на 3 дня:
1 аккаунт, 3 сценария и 100 попыток ответа. Повторный вход его не продлевает.
Существующим пользователям доступ автоматически не добавляется. Регистрацию
держите выключенной или ограниченной пилотной группой до подтверждения email и
доработки защиты от создания множества пробных аккаунтов.

Для новых покупок доступен «Старт»: 590 ₽ за 30 дней с одним Instagram-аккаунтом
и 100 ₽ за каждый дополнительный аккаунт на тот же период. При оформлении можно
выбрать от 1 до 10 аккаунтов. Включено до 5 сценариев на кабинет и автоответы
без тарифного лимита. Ранее выставленные счета принимаются по исходной сумме.

Каждая отправка клиентского аккаунта требует действующий период. Зачёт попытки
и перевод черновика в sending выполняются в одной транзакции. Учитываются
сетевые попытки, включая неуспешные и неопределённые. При исчерпании пробного
лимита или окончании доступа допустимый черновик остаётся в draft. Отправка
после возобновления доступа возможна, пока не прошло 24 часа с исходного
сообщения.

Создание сценария и добавление аккаунта проверяют лимиты на сервере. При снижении
тарифа уже сохранённые данные не удаляются; отправлять могут только первые
подключённые аккаунты и первые созданные сценарии в пределах нового лимита.
Остальные черновики ждут повышения тарифа либо удаления лишних объектов.
Статус периода, срок и квота доступны только владельцу через /api/customer/me.

`applyVerifiedPayment` — внутренний модуль для будущего платёжного адаптера.
Публичного API выдачи оплаченного периода нет. Адаптер обязан аутентифицировать подтверждение по протоколу провайдера.
Для Робокассы проверяются подпись ResultURL, сумма и данные сохранённого счёта;
возврат браузера и неподписанный webhook не подтверждают платёж. Модуль проверяет клиента, тариф, сумму в копейках, RUB и
succeeded, а ID платежа защищён уникальностью. Предоплата ставит новый 30-дневный
период после текущего/уже оплаченных, не меняя активную квоту задним числом.
Проверка подписанного ResultURL Робокассы реализована в тестируемом адаптере.
Возвраты, чеки и автоматические повторные списания пока не реализованы.
Провайдер выбран: Робокасса; заявка магазина на рассмотрении.

## Робокасса: подготовленная интеграция, магазин ещё не подключён

Провайдер выбран пользователем, заявка на рассмотрении. Адаптер и кабинет
проверены локально на синтетических подписанных уведомлениях. Реальных платежей,
тестовой операции в кабинете Робокассы и публикации приложения не выполнялось.
Документация docs.robokassa.ru из этой среды ответила HTTP 403: перед реальным
подключением сверить алгоритм подписи и параметры магазина с кабинетом/документацией.

Пока ничего не добавлено в настройки среды или Render. После одобрения магазина
значения задаются через защищённые переменные окружения:

```text
ROBOKASSA_ENABLED=true
ROBOKASSA_MERCHANT_LOGIN=<идентификатор магазина>
ROBOKASSA_HASH_ALGORITHM=sha256
ROBOKASSA_TEST_MODE=true
```

Алгоритм должен точно совпадать с настройкой магазина; поддержаны md5, sha256,
sha512. Секреты ROBOKASSA_TEST_PASSWORD1 и ROBOKASSA_TEST_PASSWORD2 задайте отдельно
в защищённых настройках. Не присылайте их в чат, не добавляйте в Git. При отсутствии
настроек кнопки оплаты выключены. По умолчанию выбран тестовый режим.

Для магазина зарегистрируйте URL (после размещения подготовленного кода):

- ResultURL: `https://vetastart-app-2026.onrender.com/webhooks/payments/robokassa`, метод POST;
- SuccessURL и FailURL: `https://vetastart-app-2026.onrender.com/billing/return`, метод GET.

ResultURL проверяет OutSum, InvId, Shp_order и SignatureValue с паролем №2,
сравнивает сумму с серверным счётом и отвечает `OK<InvId>`. Сумма не берётся
из браузера. Произвольные дополнительные Shp-параметры отклоняются. В URL оплаты
передаются подпись, непрозрачный номер заказа и описание без email клиента;
секреты в URL не включаются. Клиент видит только свои счета.

Режим счёта хранится в базе: подстановка IsTest в уведомление или последующее
переключение магазина не превратит тестовый платёж в платный. Тест получает
статус test_paid, но не выдаёт подписку. Повторный настоящий ResultURL начисляет
период только один раз по уникальному ID. Сохранение начисления и повторная
обработка позволяют восстановиться после остановки между начислением и ответом.
Новые счета можно отключить, но корректные уведомления о ранее созданных счетах
продолжат приниматься при сохранённых паролях. Не меняйте пароли или алгоритм,
пока есть неподтверждённые счета, без отдельного плана миграции.

Перед реальными платежами требуются одобрение магазина, проверка тестовой операции,
фискализации/чеков, цен и условий оплаты, затем отдельное явное включение:
ROBOKASSA_TEST_MODE=false, ROBOKASSA_LIVE_ENABLED=true и защищённые
ROBOKASSA_PASSWORD1/ROBOKASSA_PASSWORD2 для боевого режима. Сейчас это не включено.
Оплачивается один период 30 дней; рекуррентных автосписаний нет. Клиент при
необходимости оплачивает следующий период вручную. Для полной рекуррентной
подписки потребуется отдельная интеграция и согласие на повторные списания.

## Подтверждение email и восстановление доступа

Регистрация создаёт неподтверждённый аккаунт и отправляет ссылку на почту.
До подтверждения нет сессии и пробного периода; правильный пароль сам по себе
не открывает кабинет. После подтверждения нужно войти. Существующие строки
customers при миграции не считаются автоматически подтверждёнными: владельцу
нужно запросить письмо через форму в /app. Данные, сценарии и оплаченные периоды
сохраняются; уже начатый пробный период не перезапускается.

Настройки SMTP (значения не добавлялись в окружение/Render):

```text
VETASTART_MAIL_ENABLED=true
SMTP_HOST=<адрес SMTP провайдера>
SMTP_PORT=465
SMTP_USER=<пользователь SMTP>
MAIL_FROM=<адрес отправителя>
```

SMTP_PASSWORD храните в защищённых переменных. Поддержаны порт 465 с TLS или
587 с обязательным STARTTLS. Проверка сертификатов не отключается. Вызовы
Nodemailer не включают debug/logger; письма не могут загружать локальные файлы
или произвольные URL. Настройте отправителя и DNS у своего провайдера почты.
В этой среде отправка реального письма не проверена; тесты используют подмену
транспорта. Политика хранения персональных данных и настройки почтового домена
должны быть определены перед открытым коммерческим запуском.

Ссылка подтверждения действует 24 часа, сброса пароля — 30 минут. Случайный
токен имеет 32 байта, в SQLite хранится только его SHA-256. Токен передаётся
в fragment ссылки, а не query: он не попадает в URL HTTP-запроса и стандартный
access log. Страница сразу очищает адресную строку и не помещает токен в
localStorage. Действие выполняется только при отправке формы. Подтверждение
и сброс имеют разные назначения; повторное использование/неверный тип
отклоняются. После успешного действия остальные ссылки того же типа аннулируются.

Смена пароля удаляет все прежние сессии и незавершённые OAuth-запросы клиента.
Она не отключает уже подключённый Instagram и не удаляет сценарии. При ошибке
SMTP недоставленный токен удаляется; подтверждение и пробный доступ не выдаются.
Можно запросить новое письмо. Формы запроса восстановления/подтверждения
возвращают одинаковое сообщение для неизвестного и подходящего аккаунта;
это не является обещанием одинакового сетевого времени ответа. Лимиты — до
3 писем одного назначения на email и до 20 на IP за час.

Для автоматизированных локальных проверок есть VETASTART_AUTH_DEV_MODE=true:
пропуск email разрешён только на HTTP localhost/127.0.0.1. На публичном HTTPS
он не действует. Не включайте этот флаг в конфигурации размещения. Открытую
регистрацию по-прежнему контролирует VETASTART_SIGNUP_ENABLED.

Добавлен Nodemailer и package-lock.json; повторяемая установка зависимостей
теперь через npm ci. Ранее сохранённые настройки облачной среды в этой задаче
не менялись: если там осталась инструкция без lockfile, при следующем обновлении
настроек её следует привести к npm ci после проверки актуальной версии проекта.

## Проверка настроек и подготовка к размещению

`.env.example` — справочник переменных без секретов; файл сам по себе не включает
функции и автоматически Node не загружается. Для локальной проверки своего
игнорируемого .env используйте `node --env-file=.env deployment-check.js --profile pilot`.
На Render значения вводятся в Environment. При подготовке не копируйте пустые
значения поверх уже настроенных секретов.

`npm run doctor` проверяет синтаксис настроек runtime и зависимости включённых
функций. `npm run doctor -- --profile pilot` дополнительно требует параметры
Unified Login, webhook и почты. В отчёте только имена переменных и статусы;
значений, токенов, паролей или ID клиентов нет. Ненулевой exit code означает,
что выбранный профиль не настроен. Проверка не обращается к внешним сервисам,
не подтверждает токен Meta, SMTP, одобрение магазина или доступность домена.

Для production обязательны HTTPS origin, абсолютный VETASTART_DB_PATH внутри
VETASTART_PERSISTENT_DATA_DIR и выключенный режим обхода почты. Проверка путей
сама по себе не доказывает, что каталог действительно смонтирован как постоянный
диск: это нужно подтвердить в панели хостинга. Тарифы и возможности Render
проверьте в своём аккаунте до изменения инфраструктуры.

- `/health/live`: процесс отвечает, без обращения к базе.
- `/health/ready`: текущий профиль настроек валиден и запись в SQLite возможна.
  Проверка записи откатывается, не сохраняет служебные данные и не меняет очередь.
  При ошибке возвращается 503 без деталей конфигурации. Успех явно содержит
  externalServicesVerified=false: это не результат проверки Instagram или оплаты.

`render.yaml.example` — образец для ручного просмотра: один Node веб-сервис,
постоянный диск, npm ci и npm start. Это НЕ применённая конфигурация Render,
и точная схема в панели/версии Blueprint ещё не проверена. Все функции с внешними
эффектами в образце выключены; платные ресурсы не создавались, autoDeploy=false.
Не применяйте Blueprint вслепую к существующему сервису. После размещения кода
сначала подтвердите работу health/ready, затем настройте Meta и почту, выполните
пилотный профиль doctor и только потом включайте нужные функции. Робокасса
остаётся тестовой до одобрения и проверки операции.

## Резервная копия и восстановление SQLite

```sh
npm run db:backup -- /var/data/vetastart.sqlite /var/data/backups/snapshot-001.sqlite
npm run db:restore -- /var/data/backups/snapshot-001.sqlite /var/data/restored.sqlite
```

Backup использует SQLite VACUUM INTO для согласованного снимка, даже если база
открыта приложением. Файл создаётся с правами 0600, новый каталог — 0700.
Проверяются integrity_check и основные таблицы VetaStart. Restore создаёт новый
файл и отказывается перезаписывать существующий: рабочую базу не заменяет.
После проверки восстановленного файла остановите сервис/обработчики и отдельно
переключите VETASTART_DB_PATH на него; сначала сохраните текущую базу.

Снимок содержит персональные данные и зашифрованные токены. Это не шифрование
всего файла. Храните копии вне публичных каталогов, переносите и храните их по
защищённому каналу. Копия на том же диске не защищает от потери диска; нужны
отдельное защищённое хранилище и политика хранения. Восстановление токенов
требует прежнего VETASTART_TOKEN_KEY, который хранится отдельно и в снимок не
включается. В этой задаче резервное копирование проверено только на временной
тестовой базе; реальные пользовательские данные не экспортировались.

## Полное приложение на PostgreSQL

При наличии DATABASE_URL обычный npm start запускает postgres-app/start.js:
пользователи, сессии, подтверждение почты/сброс пароля, Meta OAuth, сценарии,
подписки, квоты, счета Робокассы и очередь находятся в PostgreSQL. SQLite-файлы
не создаются. Команды worker, send, automation и refresh-tokens также выбирают
этот backend. Без DATABASE_URL сохранён прежний локальный SQLite-режим.

VETASTART_PG_SCHEMA по умолчанию vetastart_pilot. Разрешены только имена с
префиксом vetastart_; public не используется для новых таблиц. Пул соединений
ограничен 8, SQL выполняется асинхронно. Транзакции используют advisory lock для
атомарных проверок владения и квот; внешние API вызываются после выхода из
транзакции. HTTP-ответ об успешной записи отправляется после COMMIT. Методы
адаптера переводят ограниченный внутренний SQL-диалект в параметризованные
PostgreSQL-запросы, значения клиентов не конкатенируются в SQL.

Данные существующего staging/cabinet-v1 в public не удаляются и не меняются.
Совместимые пользователи переносятся идемпотентным INSERT SELECT: хеш пароля
остаётся в PostgreSQL, пароль не раскрывается, старые сессии не переносятся.
Перед новым входом требуется подтверждение почты. Сохранённые проекты и
многосообщенческие сценарии прежнего кабинета доступны владельцу по его
подтверждённому email только для просмотра. Они не становятся подключёнными
Instagram-аккаунтами и не запускаются автоматически.

Подтверждено на отдельном настоящем PostgreSQL 16: регистрация/почта/сессии,
полный путь OAuth → webhook → сценарий → отправитель с подменой внешнего Meta API,
подпись и повтор оплаты, квоты между разными пулами соединений, разделение
клиентов, сброс пароля, совместимость со старыми пользователями/проектами,
перезапуск через основной server.js и откат ответов при ошибке транзакции.
Реальные внешние сервисы эти проверки не заменяют. При обычном npm test две
PostgreSQL-группы пропускаются без VETASTART_PG_TEST_URL; для проверки нужны
отдельная локальная база vetastart_test и запуск обеих integration.test.js.
Никогда не используйте рабочую базу для этих тестов.

При DATABASE_SSL=true сертификат проверяется строго. Для внутреннего Render
соединения используйте настройки существующего проверенного подключения;
TLS-проверку не отключайте ради устранения ошибки. PostgreSQL требует права
создания собственной схемы/таблиц. Автоматическая миграция не удаляет старые данные.

В Render PostgreSQL не требует локального диска веб-сервиса. Пример render.yaml
для SQLite с диском остаётся справочным и не должен применяться к уже существующему
PostgreSQL-сервису. Бесплатная Render PostgreSQL временная: перед коммерческим
запуском нужны постоянный план и резервные копии. SQLite backup/restore команды
не подходят для PostgreSQL — используйте его штатные pg_dump/pg_restore и
резервное копирование провайдера. Ключ VETASTART_TOKEN_KEY хранится отдельно.

Meta OAuth и app-level webhook подтверждены на размещённом сервисе владельца.
Пилотные ограничения остаются: реальные Direct, SMTP и тест Робокассы
нужно подтвердить на размещённом сервисе; автоматическое продление SUAT,
автосписания/чеки/возвраты Робокассы и открытый коммерческий запуск не объявляются готовыми.

## Панель владельца PostgreSQL

`/operator` использует существующий VETASTART_ADMIN_TOKEN, который вводится
в password-поле и хранится только в памяти страницы. Сценарии владельца находятся
в operator_rules и доступны только для активных подключений, не принадлежащих
клиенту. Привязка аккаунта к клиенту исключает эти сценарии из обработки.
Сценарии сохраняются, редактируются и удаляются через защищённый API.
Предпросмотр проверяет Unicode-совпадение и возвращает текст предполагаемого
ответа без создания черновиков, изменения входящих событий или обращения к Meta.

Фоновая обработка поддерживает эти сценарии на PostgreSQL. Для отправки всё ещё
требуются VETASTART_AUTOMATION_ENABLED=true и VETASTART_SEND_ENABLED=true.
Панель не меняет эти флаги. Отправитель повторно проверяет включение сценария,
источник Direct и 24-часовое окно. Операторские сценарии предназначены для
владельца сервиса; клиентские сценарии продолжают использовать подписки и квоты.
SQLite-приложение не предоставляет эту дополнительную панель.

Защищённые `/api/admin/instagram/status` и `/api/admin/instagram/diagnostics`
показывают счётчики, имя подключённого аккаунта и подписку на messages, не возвращая
токены или тексты входящих сообщений. `/api/admin/instagram/webhook` проверяет
app-level настройку, сохраняет существующие поля и отказывается перезаписывать
другой callback. Администраторские маршруты не принимают клиентские сессии.

## Резервный приём Direct через API — пилот владельца

PostgreSQL поддерживает VETASTART_API_POLL_ENABLED=true с обязательным
VETASTART_API_POLL_ACCOUNT_ID. Режим действует только для одного явно выбранного
активного Unified Login подключения без клиентского владения и с включёнными
сценариями владельца. Клиенты этим режимом не опрашиваются. Для работы нужен
VETASTART_AUTOMATION_ENABLED=true; отправка всё ещё отдельно управляется
VETASTART_SEND_ENABLED. При выключенной отправке создаются только черновики.

Интервал VETASTART_API_POLL_INTERVAL_MS — от 60000 до 3600000 мс. Состояние,
пауза между запросами и lease хранятся в базе; параллельные процессы не выполняют
один опрос одновременно. Первый запуск начинает приём с секунды включения,
старую переписку не импортирует. Повторы API и webhook объединяются по идентификатору
сообщения. После отзыва доступа опрос останавливается; ограничения Meta вызывают
увеличенную паузу. Токены, тексты переписок и ответы провайдера не записываются в лог.

За один запрос читаются до 25 переписок и до 20 последних сообщений каждой.
Если Meta указывает продолжение, статус partial сообщает об ограничении охвата;
этот пилот не гарантирует обработку произвольного объёма входящих сообщений.
Статус и время последнего опроса доступны владельцу в /operator.

Опрос работает только пока запущен процесс сервиса. Бесплатный Render засыпает
при простое, поэтому этот режим на нём не является круглосуточной автоматизацией.
Для постоянной работы нужен не засыпающий сервер. Существующий сайт и DNS Timeweb
этим изменением не переносятся и не модифицируются.
